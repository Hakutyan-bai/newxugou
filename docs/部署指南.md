# XUGOU 部署指南

本 Fork 部署到 Cloudflare Sakura 账户，使用一个 `xugou-app` Worker 承载前端、API、Cron、Queue Consumer 和 WebSocket Durable Object。

- 公开状态页：https://status.sakuraink.net/（跳转到 `/status`）
- 管理员登录：https://status.sakuraink.net/login
- 生产代码：https://github.com/Hakutyan-bai/newxugou 的 `main`
- D1：`xugou_db`；Queue：`xugou-jobs` 和 `xugou-jobs-dlq`

## 1. 本地维护与首次部署

`wrangler.toml` 是本地和 Workers Builds 共用的生产配置，包含非敏感的账户 ID、D1 ID、资源绑定和 Custom Domain。无需再渲染 D1 占位符。

使用 Node.js 22 和 pnpm 11.10.0：

```bash
pnpm install --frozen-lockfile
pnpm run ci:check
pnpm exec wrangler login
pnpm run deploy:production
```

`ci:check` 顺序执行 lint、类型检查、Worker 绑定类型一致性检查、现有后端测试、生产构建和 Wrangler dry-run。`deploy:production` 先应用尚未执行的 D1 migration，再部署 Worker；任何步骤失败即停止。仅重新发布代码时可运行 `pnpm run deploy`，但涉及数据库更新时必须使用 `deploy:production`。

主 Worker 的运行时 Secrets：

```bash
pnpm exec wrangler secret put SESSION_HMAC_SECRET
pnpm exec wrangler secret put AGENT_TOKEN_PEPPER
pnpm exec wrangler secret put NOTIFICATION_KEK
pnpm exec wrangler secret put ADMIN_INITIAL_PASSWORD
```

以上命令通过交互输入密钥。首次部署自动生成这些值，保存在仓库外、仅当前 Windows 用户可读的 `%LOCALAPPDATA%\CodexDeployments\xugou` 目录。`initial-admin.txt` 包含管理员登录信息，`worker-secrets.json` 用于密钥备份。不要把该目录或文件提交到 Git。三个长期密钥必须保持稳定，通知 KEK 轮换遵循配置中的版本和轮换开关。

`ADMIN_INITIAL_PASSWORD` 只在空数据库第一次使用正确凭据登录时创建 `admin`，至少 12 位。已有数据库继续使用原账号数据。前端和 API 同源；`/api/*` 优先交给 Worker，其他路径由静态资源提供 SPA 页面。

## 2. GitHub 推送自动上线

Cloudflare Worker 的 Settings > Builds 关联 `Hakutyan-bai/newxugou`：

| 设置 | 值 |
| --- | --- |
| Production branch | `main` |
| Root directory | `/`（仓库根目录） |
| Build command | `pnpm run ci:check` |
| Deploy command | `pnpm run deploy:production` |
| Build variable `NODE_VERSION` | `22` |
| Build variable `PNPM_VERSION` | `11.10.0` |
| Preview / non-production builds | 禁用 |

依赖安装使用锁文件；仓库 `packageManager` 固定 pnpm 版本。Workers Builds 的部署令牌需具有该账户的 Workers Scripts、D1、Queues、Durable Objects，以及域名部署所需的 Workers Routes 权限。运行时四个 Secrets 保存在 Worker 上，不作为构建变量，不写入 GitHub。

`.github/workflows/deploy.yml` 仅执行检查，不部署生产环境。生产发布统一由 Workers Builds 完成，避免两个流水线同时迁移和发布。

### 日志与回滚

```bash
pnpm exec wrangler deployments status --name xugou-app
pnpm exec wrangler d1 migrations list xugou_db --remote
pnpm exec wrangler tail xugou-app
pnpm exec wrangler versions list
pnpm exec wrangler rollback <VERSION_ID>
```

Workers Builds 页面可查看每次提交的构建结果和日志。发布失败时保留上一个 Worker 版本；数据库迁移与代码发布不是原子操作，失败后应排查迁移兼容性再重试。回滚 Worker 不会回滚 D1 schema，涉及数据时先使用 D1 导出或 Time Travel。代码回滚后同步修正 `main`，避免下次推送重新发布错误版本。

本次部署保留 `FREE_MODE=true`，只初始化平台。监控对象、通知渠道及下面的 Agent 二进制发布服务后续配置。

## 3. Agent 下载发布

Agent 二进制使用独立 R2 Bucket。发布工作流只写以下对象：

```text
latest/manifest.json
latest/xugou-agent-linux-amd64
latest/xugou-agent-linux-arm64
latest/xugou-agent-darwin-amd64
latest/xugou-agent-darwin-arm64
latest/xugou-agent-windows-amd64.exe
latest/xugou-agent-windows-arm64.exe
```

`latest/manifest.json` 内嵌 Ed25519 签名，不使用分离签名、版本归档或 channel 对象。`Build and Publish Agent` Environment 需要：

| Secret | 用途 |
| --- | --- |
| `AGENT_UPDATE_PUBLIC_KEY` | Base64 编码的 32 字节 Ed25519 公钥 |
| `AGENT_UPDATE_PRIVATE_KEY_B64` | Base64 编码的 Ed25519 私钥 |
| `R2_ACCESS_KEY_ID` | R2 S3 API Access Key |
| `R2_SECRET_ACCESS_KEY` | R2 S3 API Secret |
| `R2_ACCOUNT_ID` | R2 所属 Account ID |
| `R2_BUCKET_NAME` | Agent 下载 Bucket 名称 |

发布 GitHub Release 或手动运行 `.github/workflows/build.yml`，并传入 SemVer。工作流先构建六个平台产物，再更新二进制，最后切换 `latest/manifest.json`。

## 4. 验证

```bash
pnpm exec wrangler d1 migrations list xugou_db --remote
pnpm exec wrangler deployments status --name xugou-app
curl -fsS https://dl.xugou.mdzz.uk/latest/manifest.json
```

Agent 上行使用 Bearer 鉴权的 `/api/v2/agents/live`；状态页下行使用 `/api/v2/status/public/ws`，管理端下行使用 `/api/ws`。三条链路均由 `AgentRoom` Durable Object 提供，实时样本不写 D1，也不消耗 Queue 消息额度。

上行帧按 `--live-interval`（默认 12 秒）攒批发送，不是每次采集发一帧：Durable Object 的**每条入站 WebSocket 消息都单独计一次 Worker 请求**，秒级一帧时单台探针就是 86400 次/天，免费额度一台就用光。攒批只增加实时视图的延迟，批内仍是逐秒样本，采样精度和 D1 里的历史都不受影响。调小这个值会按比例放大 Worker 请求数——排查每日额度告警时先看它。

实时上行**只接受攒批帧**（`{"type":"metric_batch","protocol_version":2,…}`）。v1.4.0 到 v1.4.1 之间曾并行接受 v1 单点帧供存量探针过渡，v1.4.2 起已移除：**低于 v1.4.0 的探针实时链路会被 `close(1008)`**，需先升级探针。历史上报不受影响，那条走 HTTP，与实时通道完全独立。

在此之上还有**按需推流**：`AgentRoom` 统计每个 Agent 的下行订阅者，数量从 0 变正、从正变 0 时给探针下发一次 `{"type":"stream","enabled":…}`，只在边沿下发——每个订阅者都发一条的话，指令自己就成了新的请求源。探针重连时从 `hello` 的 `stream` 字段对齐当前状态。无人观看时探针一帧不发，但**采集和缓冲照常**，缓冲约 100 秒，恢复观看时立刻补上这一段。

两条安全阀不能动：探针默认常开，且收到不带 `stream` 的 `hello`（旧服务端）时会恢复常开——否则服务端一回滚，暂停中的探针会永久静默。历史精度与实时通道无关：`agent_metric_blocks` 与 `last_seen_at_ms` 只有 `D1AgentReportIngestor` 一个写入者，由 HTTP `/api/v2/agents/reports` 驱动，`AgentRoom` 一行 D1 都不写。
